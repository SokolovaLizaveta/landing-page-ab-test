# A/B-тест посадочной страницы

Учебный проект по анализу A/B-теста посадочной страницы интернет-магазина Maven Fuzzy Factory.

Цель проекта — восстановить параметры исторического эксперимента по сырым данным, сформулировать дизайн A/B-теста и оценить, показывает ли новая посадочная страница статистически значимое улучшение основной метрики.

## Источник данных и права на использование

В проекте используется набор данных **Toy Store E-Commerce Database** из [Maven Analytics Data Playground](https://mavenanalytics.io/data-playground/toy-store-e-commerce-database).

На странице датасета Maven Analytics указано:

- **Source:** Maven Analytics;
- **License:** Public Domain.

Датасет содержит данные интернет-магазина Maven Fuzzy Factory: пользовательские сессии, просмотры страниц, заказы, товары и возвраты.

Идея анализа основана на публичной формулировке guided project
[Landing Page A/B Test от Maven Analytics](https://mavenanalytics.io/guided-projects/landing-page-a-b-test):

> Analyze bounce rates from a landing page A/B test to see if the new home page shows a statistically significant improvement.

То есть необходимо проанализировать bounce rate A/B-теста посадочной страницы и проверить, показывает ли новая страница статистически значимое улучшение.

Подробные инструкции guided project в этом репозитории не воспроизводятся, так как подробности эксперимента доступны только в платной версии. Параметры эксперимента, такие как мощность и порог значимости, были выбраны самостоятельно. Период проведения и тестовый сегмент были восстановлены на основе исходных данных. Для дальнейшего статистического анализа самостоятельно были заданы уровень значимости α = 0.05 и целевая мощность 80%; эти значения не утверждаются как исходные параметры исторического эксперимента.

Проект создан в учебных целях и не является официальным решением Maven Analytics и никак не связан с Maven Analytics.

Подробнее о структуре данных смотреть в [`data_dictionary.md`](data_dictionary.md) (в этом же файле приведена ER-схема базы данных).

## Постановка A/B-теста

### Бизнес-вопрос

Показывает ли новая главная страница статистически значимое снижение bounce rate по сравнению со старой страницей?

Старая посадочная страница рассматривается как контрольный вариант, новая - как тестовый.

### Гипотезы

Обозначим:

- $p_{old}$ — bounce rate старой страницы;
- $p_{new}$ — bounce rate новой страницы.

Тогда проверяются односторонние гипотезы:

$$ H_0: p_{new} \ge p_{old} $$

$$ H_1: p_{new} < p_{old} $$

То есть нулевая гипотеза соответствует отсутствию улучшения, а альтернативная — снижению bounce rate на новой странице.

### Метрики

**Primary metric**

**Bounce rate** - доля сессий, в которых пользователь просмотрел только одну страницу и не перешёл дальше в рамках этой сессии:

$$ Bounce\ Rate =
\frac{\text{сессии с одним pageview}}
{\text{все сессии}} $$

**Secondary metrics**

- **Conversion to order** — доля сессий, завершившихся заказом;
- **Revenue per session** — средняя выручка на одну сессию.

**Guardrail metric**

**Conversion to order** — новая посадочная страница не должна приводить к существенному ухудшению конверсии в заказ. Конверсия в заказ используется как защитная метрика, поскольку снижение bounce rate само по себе не гарантирует улучшения бизнес-результата. Новая посадочная страница может побуждать пользователей чаще переходить дальше по сайту, но при этом снижать вероятность покупки.

## Реконструкция эксперимента

Подробная логика исследования исходных данных находится в [`sql/03_experiment_reconstruction.sql`](sql/03_experiment_reconstruction.sql).

Поскольку параметры (время, сегмент пользователей) исторического эксперимента не были доступны в открытом описании проекта, они восстанавливались непосредственно из данных. 

### 1. Поиск новой посадочной страницы

В таблице `website_pageviews` было найдено первое появление страницы `/lander-1`:

**2012-06-19 00:35:54**

Это стало отправной точкой для поиска возможного начала эксперимента.

### 2. Определение landing page каждой сессии

Для каждой сессии была определена первая просмотренная страница с помощью оконной функции `ROW_NUMBER()`.

Это позволило рассматривать `/home` и `/lander-1` именно как посадочные страницы, а не как страницы, которые пользователь мог открыть позже внутри сессии.

### 3. Поиск тестового сегмента

Далее было исследовано распределение `/home` и `/lander-1` по `utm_source` и `utm_campaign`.

Обе страницы одновременно встречались только в одном сегменте:

```text
utm_source   = gsearch
utm_campaign = nonbrand
```

Поэтому этот сегмент был выбран как наиболее вероятный трафик A/B-теста.

### 4. Восстановление периода эксперимента

Первое появление `/lander-1` в сегменте `gsearch / nonbrand`: 2012-06-19 00:35:54.

Последняя сессия с `/home` в этом же сегменте — 2012-07-29 23:48:16. После этого, как видно из данных, в качестве посадочной страницы используется только `/lander-1`.

На основании этих наблюдений рабочее окно A/B-теста было реконструировано как период **с 19 июня по 29 июля 2012 года**.

Повторно подчеркну - это реконструированный по данным период, а не подтверждённый официальный интервал эксперимента.

### 5. Проверка распределения трафика

В реконструированном окне теста получены следующие размеры групп:

| Вариант | Landing page | Сессии |
|---|---|---:|
| Control | `/home` | 2328 |
| Treatment | `/lander-1` | 2381 |

Распределение близко к 50/50, что согласуется с предположением о разделении трафика между двумя вариантами страницы.

### 6. Предтестовый baseline

Для оценки исходного уровня bounce rate был использован тот же сегмент `gsearch / nonbrand` до появления `/lander-1`.

До начала реконструированного теста в этом сегменте было 10 677 сессий, и их посадочной страницей была только `/home`.

Рассчитанный предтестовый baseline:

**Bounce rate = 60.99%**

Этот показатель использовался далее при оценке мощности эксперимента.

## Ретроспективная оценка MDE и мощности

Расчёты находятся в [`notebooks/01_experiment_design.ipynb`](notebooks/01_experiment_design.ipynb).

Исходный MDE, который мог быть выбран командой до запуска исторического эксперимента, неизвестен. Поэтому вместо попытки приписать эксперименту неизвестный бизнес-порог по фактическому размеру выборки была ретроспективно оценена величина эффекта, которую такой тест способен обнаружить с заданной мощностью.

Здесь и далее в тексте будут использоваться округлённые значения для некоторых показателей, для уточнения следует обращаться к указанным файлам, в которых проводились точные расчёты.

Для расчёта использовались:

- baseline bounce rate: **60.99%**;
- control group: **2328 сессий**;
- treatment group: **2381 сессия**;
- уровень значимости: **α = 0.05** (задан самостоятельно);
- целевая мощность: **80%** (задана самостоятельно);
- односторонняя альтернатива.

Расчёт выполнен в Python с использованием `statsmodels.stats.power.NormalIndPower` и `proportion_effectsize`.

Сначала мощность была рассчитана для широкого диапазона возможных эффектов, после чего диапазон последовательно сужался около уровня мощности 80%.

Получено:

| MDE | Power |
|---:|---:|
| 3.55 п.п. | 79.7896% |
| 3.56 п.п. | 79.9845% |
| 3.57 п.п. | 80.1783% |

Таким образом, при фактическом размере выборки эксперимент способен обнаружить снижение bounce rate примерно на **3.56 п.п.** с мощностью около **80%** при уровне значимости **0.05**.

При baseline 60.99% это соответствует bounce rate новой страницы примерно **57.43%** или ниже.

Это значение является **ретроспективно оценённым detectable effect**, а не подтверждённым исходным MDE, который был выбран командой до запуска эксперимента.


## Подготовка данных для анализа A/B-теста

После реконструкции параметров эксперимента была создана отдельная аналитическая таблица `experiment`.

SQL-код её формирования находится в [`sql/04_experiment.sql`](sql/04_experiment.sql).

В таблицу вошли сессии сегмента `gsearch / nonbrand` за реконструированный период эксперимента, для которых первой просмотренной страницей была `/home` или `/lander-1`.

**Единица наблюдения — пользовательская сессия.** Для каждой сессии были рассчитаны или сохранены следующие признаки:

- `website_session_id` — идентификатор сессии;
- `session_created_at` — дата и время начала сессии;
- `device_type` — тип устройства;
- `is_repeat_session` — признак повторной сессии;
- `landing_page` — первая просмотренная страница;
- `pageviews` — количество просмотров страниц за сессию;
- `bounced` — бинарный признак (1, если просмотрена только одна страница, иначе 0);
- `is_order` — признак наличия заказа в сессии;
- `revenue` — суммарная выручка от заказов в рамках сессии, USD.

Итоговая таблица содержит **4709 сессий**: 2328 в контрольной группе и 2381 в экспериментальной.

Таблица была экспортирована в [`data/experiment.csv`](data/experiment.csv) для дальнейшего анализа в Python. Этот CSV является производным файлом, сформированным в рамках проекта, а не отдельным исходным датасетом Maven Analytics.

## Анализ результатов A/B-теста

Полный анализ, расчёты статистических тестов и интерпретация результатов находятся в [`notebooks/02_ab_test_analysis.ipynb`](notebooks/02_ab_test_analysis.ipynb).

### 1. Sanity checks

Перед анализом метрик были проведены проверки качества и распределения экспериментальных данных.

**Sample Ratio Mismatch (SRM).** Проверялось соответствие фактического распределения сессий предполагаемому соотношению 50/50. Для этого использовался χ²-критерий согласия. Статистически значимых отклонений от предполагаемого распределения 50/50 не обнаружено.

**Баланс групп по типу устройства.** Для проверки распределения `desktop` и `mobile` между контрольной и экспериментальной группами использовался χ²-критерий независимости. Статистически значимых различий в составе групп по типу устройства не обнаружено.

**Повторные сессии.** Проверка признака `is_repeat_session` показала, что во всех 4709 наблюдениях он равен 0. Поэтому данный признак не использовался для дальнейшей сегментации.

**Стабильность распределения трафика во времени.** Была рассчитана доля сессий экспериментальной группы по каждому дню. Наблюдались отдельные отклонения от 50/50, однако устойчивого тренда в распределении трафика не обнаружено. Доля `/lander-1` по дням изменялась примерно от 0.41 до 0.64.

Проведённые проверки не выявили статистически значимых нарушений исследованных характеристик распределения трафика.

### 2. Анализ основной метрики — Bounce rate

Для сравнения bounce rate между контрольной и экспериментальной группами использовался **двухвыборочный z-тест для пропорций**, поскольку бизнес-гипотеза заключалась именно в снижении доли отказов.

Получены следующие результаты:

| Показатель | Значение |
|---|---:|
| Bounce rate `/home` | 58.63% |
| Bounce rate `/lander-1` | 53% |
| Абсолютное изменение | −5.63 п.п. |
| Относительное изменение | −9.6% |
| z-статистика | −3.8901 |
| p-value | 0.00005 |
| 95%-й ДИ для разницы | [−8.46; −2.80] п.п. |

При уровне значимости 5% нулевая гипотеза отвергается. Новая посадочная страница `/lander-1` показывает статистически значимое снижение bounce rate относительно `/home`.

Наблюдаемое снижение 5.63 п.п. превышает ретроспективно оценённый MDE 3.56 п.п. Однако доверительный интервал допускает и меньшую величину истинного снижения. Кроме того, поскольку заранее установленный бизнес-порог успешности исторического эксперимента неизвестен, статистическая значимость не означает автоматически доказанную бизнес-значимость результата.

### 3. Анализ Conversion to order

Conversion to order рассматривалась, во-первых, как **guardrail-метрика**, во-вторых, как **secondary-метрика**.

Её анализ необходим, поскольку снижение bounce rate само по себе не гарантирует улучшения бизнес-результата: пользователи могут чаще переходить на следующие страницы, но реже совершать покупки.

| Показатель | Значение |
|---|---:|
| Conversion to order `/home` | 3.22% |
| Conversion to order `/lander-1` | 4.03% |
| Абсолютное изменение | +0.81 п.п. |
| Относительное изменение | +25.15% |
| p-value одностороннего теста на снижение | 0.93137 |
| 95%-й ДИ для разницы | [−0.26; 1.88] п.п. |

Для guardrail-проверки использовался z-тест для пропорций, направленный на выявление возможного снижения конверсии.

Статистически значимых свидетельств ухудшения conversion to order не обнаружено. Однако 95%-й доверительный интервал включает отрицательные значения, поэтому полностью исключить небольшое снижение конверсии нельзя.

Для строгой проверки допустимости возможного ухудшения guardrail-метрики необходим заранее установленный порог снижения конверсии.

### 4. Анализ Revenue per session

Для Revenue per session были получены следующие значения:

| Показатель | Значение |
|---|---:|
| Revenue per session `/home` | 1.61 USD |
| Revenue per session `/lander-1` | 2.02 USD |
| Абсолютное изменение | +0.4051 USD |
| Относительное изменение | +25.15% |

При изучении распределения `revenue` было обнаружено, что в экспериментальной выборке этот признак принимает только два значения: `0.00` и `49.99` USD.

Следовательно, на уровне сессии выполняется точное соотношение:

$revenue = 49.99 \cdot is\_order$.

А на уровне группы:

$Revenue\ per\ session = 49.99 \cdot Conversion\ to\ order$.

Таким образом, Revenue per session в рассматриваемой выборке является точным линейным преобразованием conversion to order.

Поэтому отдельный статистический тест не проводился. Вместо этого уже полученный доверительный интервал для разницы conversion to order был преобразован в денежные единицы:

$49.99 \cdot 0.01 \cdot [-0.2569;\ 1.8774] = [-0.1284;\ 0.9385]$ USD на сессию.

Полученный 95%-й доверительный интервал ожидаемо включает 0. Следовательно, статистически значимое различие Revenue per session между группами не установлено.

### 5. Сегментация эффекта по типу устройства

После анализа общих результатов было исследовано, различается ли эффект новой посадочной страницы для пользователей `desktop` и `mobile`.

Другие признаки оказались непригодны для содержательной сегментации: часть характеристик использовалась при выделении экспериментального трафика и была постоянной, а `is_repeat_session` оказался равен 0 для всех наблюдений.

Для каждого типа устройства отдельно были рассчитаны bounce rate контрольной и экспериментальной групп, разница между ними и 95%-й доверительный интервал.

| Тип устройства | Изменение bounce rate | 95%-й ДИ |
|---|---:|---:|
| Desktop | −6.93 п.п. | [−10.18; −3.67] п.п. |
| Mobile | −0.80 п.п. | [−6.22; 4.61] п.п. |

Для `desktop` доверительный интервал полностью находится ниже нуля, что указывает на снижение bounce rate для новой страницы. Для `mobile` интервал включает 0, поэтому статистически значимое изменение не установлено.

Однако различие в результатах отдельных сегментов само по себе ещё не доказывает, что эффекты новой страницы для них действительно различаются.

Поэтому дополнительно была проведена **проверка различия двух независимых оценок эффекта**. Сравнивались абсолютные изменения bounce rate для `desktop` и `mobile` с использованием z-статистики и стандартной ошибки разности эффектов.

Получено:

- наблюдаемая разность эффектов: **−6.13 п.п.**;
- `p-value = 0.0577`;
- 95%-й доверительный интервал: **[−12.46; 0.20] п.п.**

При уровне значимости 5% нулевая гипотеза о равенстве эффектов не отвергается. Несмотря на заметное различие точечных оценок, данных недостаточно, чтобы статистически подтвердить зависимость эффекта новой посадочной страницы от типа устройства.

## Использование посадочных страниц после эксперимента

Дополнительно в [`sql/03_experiment_reconstruction.sql`](sql/03_experiment_reconstruction.sql) было исследовано использование `/home` после окончания реконструированного периода A/B-теста.

Начиная с **30 июля 2012 года** в сегменте `gsearch / nonbrand` не обнаружено ни одного просмотра старой посадочной страницы `/home`.

При этом на всём сайте после той же даты было зафиксировано **122 812 просмотров `/home`**, относящихся к другим сегментам трафика.

Таким образом, старая страница продолжала использоваться на сайте, но перестала встречаться в исследуемом сегменте.

Этот результат согласуется с предположением, что после эксперимента новую посадочную страницу могли закрепить за сегментом `gsearch / nonbrand`, не распространяя изменение на весь трафик.

Однако факт принятия такого решения, его причины и конкретные параметры последующего распределения трафика невозможно достоверно установить по имеющимся данным.

## Итоговые результаты

**Главный результат проекта — статистически значимое снижение bounce rate на новой посадочной странице `/lander-1` относительно `/home` на 5.63 п.п. (9.60% относительно контрольной группы).**

При этом:

- статистически значимого ухудшения conversion to order не обнаружено, но небольшой отрицательный эффект полностью исключить нельзя;
- Revenue per session показывает положительную точечную оценку, однако статистически значимое различие также не установлено;
- снижение bounce rate заметно сильнее в сегменте `desktop`, но статистически значимое различие эффектов между `desktop` и `mobile` не подтверждено;
- после реконструированного периода эксперимента `/home` перестала встречаться в исследуемом сегменте, продолжая использоваться в других сегментах сайта.

### Ограничения исследования

Основное ограничение — отсутствие доступа к исходному дизайну исторического A/B-теста.

Период проведения эксперимента, тестовый сегмент и предполагаемое распределение трафика были реконструированы самостоятельно. Уровень значимости 5% и целевая мощность 80% также были выбраны в рамках данного анализа, а не получены из документации исторического эксперимента.

Неизвестны исходный MDE, бизнес-критерии успешности, допустимые пороги ухудшения guardrail-метрик и правила принятия решения об окончании эксперимента.

Поэтому ретроспективно рассчитанный MDE и проведённые статистические проверки нельзя считать восстановлением исходного статистического плана команды.

Полученные результаты позволяют сделать вывод о статистически значимом снижении основной метрики в исследуемом сегменте, однако для оценки бизнес-значимости и более определённых выводов о вторичных метриках необходима дополнительная информация.

## Воспроизведение анализа

Для воспроизведения проекта необходимы PostgreSQL, Python и исходные CSV-файлы набора данных Maven Analytics.

Порядок работы:

1. Выполнить `sql/00_setup.sql` для создания базы данных ab_test_project. Затем подключиться к созданной базе данных и выполнить `sql/01_create_tables.sql`.
2. Загрузить исходные CSV-файлы в соответствующие таблицы PostgreSQL.
3. Выполнить `sql/02_data_check.sql` для первоначальной проверки данных.
4. Изучить и выполнить `sql/03_experiment_reconstruction.sql` для восстановления экспериментального сегмента и периода.
5. Выполнить `sql/04_experiment.sql` для формирования аналитической таблицы `experiment`, после чего экспортировать её в `data/experiment.csv`.
6. Открыть `notebooks/01_experiment_design.ipynb` для воспроизведения расчётов мощности и MDE.
7. Открыть `notebooks/02_ab_test_analysis.ipynb` для проведения sanity checks, статистических тестов, анализа метрик и сегментации.

Для анализа в Python использовались библиотеки `pandas`, `numpy`, `scipy`, `statsmodels` и `matplotlib`.

Подробные объяснения статистических методов, код и промежуточные результаты сохранены в соответствующих ноутбуках.
